# How fast-moving projects keep full test runs short

Part 2 of the test-speed work (`perf/test-speed`). Each source says what the project does; each technique ends with whether it applies here, the gain expected **given the Part 1 profile** ([PROFILE.md](PROFILE.md)), the risk to test fidelity and the effort. Results of what was tried are in [RESULTS.md](RESULTS.md).

**Verified** = I read the primary source (the repository at the commit given, or the official docs page) on 2026-11-10. **Secondhand** = a blog, a summary, a search snippet or my own prior knowledge, not checked against the primary source; treat its numbers as claims.

The profile facts these judgements rest on (Lenovo, 10 cores, quiet machine, `restructure/integration` 2917a115 + the harness):

- `all` 275 s wall, 941 CPU-s: 34% of the cores. Critical path: plugin build (9 s) → test-project build + Architecture tests (10 s) → T (85 s, the xUnit `Plugin singleton` collection runs 77 classes / 50 s one after another) beside the frontend suite (72 s, bounded by one 72 s file) → `F` rest (106 s, almost serial: client-build tests at concurrency 1, the contract-boundary test, contracts, checks) → fe (15 s) → **the client-build tests a second time** (45 s).
- `browser` 193 s wall, 755 CPU-s (39%), 693 tests = 231 × {chromium, mobile-chromium, firefox}, 968 test-seconds over 6 workers. Its longest tests are frame-bound (rAF waits), not CPU-bound: `tag-fit-monotonic` spends 94 s per project for 9–22 CPU-s.
- The full TypeScript check (`tsc` 6 API, ~3.7 s, single-threaded) runs about 7 times per `all`: inside each of the three dotnet builds (MSBuild target `VerifyJellyfinEnhancedClient`), `client:check` twice, `client:typecheck`, `client:build`, plus 4 fixture checks in the contract-boundary test.

## 1. The sources

### T3 Code (`pingdotgg/t3code`) — verified (shallow clone of `main` at f7281124, 2026-11-09)

- **Runner and layout.** pnpm workspace driven by Vite+ (`vp`): Vitest for tests, `vp run -r --cache` for per-package tasks. `apps/server` sets `fileParallelism: false` (`apps/server/vite.config.ts:151`): its test files run one at a time for isolation.
- **What runs per change.** `.github/workflows/ci.yml` starts with a `changes` job: `.github/scripts/ci-changes.cjs` maps changed files to workspace packages **and their dependents** and skips jobs a change cannot affect. It **fails open**: an unknown path, or a diff it cannot resolve, runs everything. It keeps explicit lists of reads the package graph misses (`EXTRA_OWNERS`, `TEST_ONLY_DEPS`, `BUILD_ONLY_DEPS`, `RUNS_EVERYTHING`). Pushes to `main` run every Linux job. Locally, agents run `vp run check:changed` (`scripts/check-changed.ts`, shares `ci-changes.cjs`): format/lint of changed files, typecheck of affected packages and dependents, the tests beside the changed files; steps run side by side within a budget of one step per 2 cores and 6 GiB, each killed at a timeout; a rerun on exactly the files of the last passing run prints that run's summary. `AGENTS.md`: "Do not run repo-wide checks … CI owns the full suite."
- **Content-addressed test caching.** `scripts/test-cached.ts` + `scripts/lib/cached-tests.ts`: each test file becomes its own Vite+ task whose cache input is `{ auto: true }`, i.e. the files the task actually read (fs tracking), minus Vitest's own caches. A hit replays the result. `--verify-hits N` re-runs N randomly chosen hits **without** the cache in the same CI run and fails if one fails: a continuous audit of cache correctness. Files listed with `--uncached` always run.
- **Duration-based sharding.** `test_server` runs 8 shards on 4-vCPU runners; `apps/server/src/testUtils/weightedShardSequencer.ts` assigns files greedily, longest recorded duration first (`shardWeights.json`, unrecorded files 0.6 s). Comment: one file at a time keeps ~1.5 cores busy, so 4 vCPUs lose nothing against 8.
- **Overlap inside a job.** The typecheck starts in the background while the desktop build runs and reports in the last step ("neither result hides the other"). Apt installs run in the background during dependency install.
- **Type checker.** Every package's typecheck is `effect-tsgo tsrs --noEmit`: "the Rust TypeScript 7 checker with Effect's diagnostics built in. There is no `typescript` package to run" (`AGENTS.md` "Verifying"). So T3 Code already gates on the ts-rust checker.
- **Test-writing rules that keep suites fast.** "Never wait on sleeps or polling. A test that needs a timeout to pass is wrong." Await the specific event instead.
- Not found in the repository: anything about "hundreds of pull requests a day" beyond `pr-size.yml`/`agent-context-budget.yml` workflows; I did not find a written post on it (secondhand claims exist on social media; not used).

### ts-rust / tsc-rs (`pingdotgg/ts-rust`) — verified (README at 91f3d021, 2026-10-28; npm metadata 2026-11-10)

- **What it is.** A Rust port of Microsoft's Go TypeScript 7 compiler, written by LLM agents (author: "I've never read a line of this code"; "This is an early release"). It keeps the Go version's algorithms, command line, language server (`--lsp`) and API server (`--api`).
- **Coverage today.** Type checking (claims diagnostics identical to Go's on its corpus: 13,728 compiler configurations, 186,890 ported and own tests passing), emit (13,654/13,654 byte-identical emit checks, source maps), `tsc -b` (project references, with a known difference when one project reads another's output without a reference), `--watch` (it ships a file watcher; the README documents none of its behaviour), the language server and API. Options: "the same options as `tsc`", i.e. TypeScript 7's set (no `baseUrl`, no `moduleResolution: node10`, no `target: es5`). Declaration emit is not described separately. Effect diagnostics are built in (on only with the `@effect/language-service` plugin in `tsconfig`).
- **Known gaps (README).** Monorepo sources reachable through both `node_modules` and a direct import can give extra output and TS6059; `tsc -b` without references can differ from `tsc`; editor memory grows slowly; `--version` prints the ported TypeScript version (7.1.0-dev / 7.1.0-beta), not the package version.
- **Release state.** npm `tsc-rs` versions 0.1.0 (2026-10-07) to **0.8.0 (2026-10-21, `latest`)**; `@tsc-rs/typescript@0.8.0` is a drop-in alias for the `typescript` package. 0.4.0–0.8.0 port the 2026-10-08 upstream pin (`typescript@7.1.0-dev.20261008.1`); the README's oracle for comparisons is that version, not 7.0.x. Platforms: Linux x64/arm64, macOS, Windows (per-platform optional packages `@tsc-rs/<os>-<arch>`).
- **Install.** `npm install -D tsc-rs` (the binary comes from the platform optional dependency; the `postinstall` is not needed: it worked here with npm's install scripts blocked), or the per-release archive. Reproducible offline install: pin `tsc-rs@0.8.0` in `package.json`/`package-lock.json` (with the `@tsc-rs/linux-x64` integrity hash) so `npm ci` from a populated cache works without network, as for esbuild today.
- **Speed (author's numbers, secondhand until RESULTS.md).** About half of Go's time on 60 projects (geometric mean); `--fast` (one checker per core, up to 16) 2.90× `tsc` 7 against 2.10× default on six apps; "the gain is small or zero on small projects".

### Microsoft TypeScript 7 (`tsgo`) — verified (TS 7.0 RC post, 2026-06-18; npm `typescript` dist-tags 2026-11-10)

- TypeScript 7.0 is the Go port, shipped in the **`typescript` package itself** (`latest` = **7.0.2**; `next` = 7.1.0-dev nightlies). `@typescript/native-preview` (the `tsgo` binary) carried the pre-release nightlies and stopped at `7.0.0-dev.20260707.2`.
- Type checking is meant to match 6.0 ("you should see the same results as before – just much faster"); about 10× faster than 6.0 from native code and shared-memory parallelism; `--checkers N` (default 4), `--builders`, `--singleThreaded`; `--watch` rebuilt. **No stable programmatic API until 7.1** — relevant here, because `scripts/client-build.mjs` drives the TypeScript 6 API in-process (`ts.createProgram`, `ts.createSourceFile` for the source policy, `ts.parseJsonText`). `@typescript/typescript6` provides `tsc6` and the 6.0 API for side-by-side use.

### Anthropic: code review and CI at Claude Code's volume — verified (both posts)

- [Solving code review at Anthropic](https://claude.dev/blog/solving-code-review-at-anthropic/): required checks are "lint, type checks, tests on every platform, and a build"; "a typical CLI pull request may run dozens of checks before anyone looks at it"; **"The merge queue re-runs every check against main with the change applied, so two PRs that pass separately can't combine into a broken main."** Before a PR exists the agent is given "something it can run—like tests, a build or a screenshot" and must show the output. After merge: flags, a `latest` channel ahead of `stable`, reverts.
- [Agentic coding is straining CI: test impact analysis at Anthropic](https://claude.com/blog/agentic-coding-is-straining-ci-heres-how-we-scaled-test-impact-analysis-at-anthropic): CI job volume rose 25× in six months; "not every test runs on every PR": a deterministic selection service "determines which tests run on each change based on past performance and package relevance", fed by a listener that records every CI result into per-test history. Its failure modes are the interesting part: when history lags, the selector misses newly added or fixed tests and runs already-broken ones. The post gives no miss rate and does not describe fallbacks; the merge queue (above) is what makes selection on PRs safe.

## 2. The techniques, judged against this repository

Gains are for the 10-core Lenovo unless stated. "Critical path" means the gain shows in wall time only if the step is on it.

| # | Technique | Applies here? | Expected gain (from the profile) | Fidelity risk | Effort |
|---|---|---|---|---|---|
| 1 | **Do repeated work once.** One build for G and T (`--no-build`); in `all`, do not re-run what `be` ran on the same tree (`test:client-build` twice, `client:check` ×2, `inventory:rewrite:check` ×2, INV ×2, TOOL ×2, `client:typecheck` ⊂ `client:build`). | Yes: the profile shows each one. `gate_all` already proves the tree unchanged between be and fe, which is what makes the second run redundant (it already skips the second frontend-suite run on that ground). | ~45 s (second client-build tests, on the critical path) + ~12 s (T's rebuild before its test host starts) + ~5 s (G's rebuild). | None: the same tests run once on the same inputs. Only repeated runs disappear. | Small. |
| 2 | **Run independent suites at once against one build** (DAG instead of a line): node suites need no dotnet build at all and can start at t=0; dotnet lane B → build → G → T; contracts/boundary lane; checks lane. | Yes. Today only T ∥ frontend suite overlap; F's 106 s and fe's 60 s run after both. | `all` bounded by max(dotnet lane ~95 s, CPU/cores ~90 s) instead of the sum: roughly 275 → 120–150 s. | Low if (a) the tree check compares start and end of the whole run, (b) every lane's ratchet still runs, (c) load-sensitive tests are fixed first (item 6), since concurrency raises load. | Medium (gate script). |
| 3 | **Parallelise inside suites that are needlessly serial.** `test:client-build` uses `--test-concurrency=1` with no shared state. | Yes. | 45 s → ~24 s (its slowest file). | None if the files share nothing (checked: all use their own `mkdtemp` fixtures); proved by repeated parallel runs. | Trivial. |
| 4 | **Split by measured duration / longest first.** Node runs files alphabetically; one 72 s file bounds the frontend suite; Playwright's longest tests (`tag-row-subpixel` 33 s, `tag-fit-monotonic` 16–19 s each) sit late in the order. | Yes for node (split the 72 s file or order longest-first); Playwright has no custom order, so only more workers or splitting help. | Frontend suite 72 → ~55 s (CPU-bound at 9 workers: 487 CPU-s / 9). | None for ordering; splitting a file changes test ids (the ratchet keys on `file :: name`), counts stay. | Small. |
| 5 | **More workers where the work waits, not computes.** Browser tests use ~4 cores at 6 workers because the long tests wait on frames. | Yes for Playwright. | 968 test-seconds / 10 workers ≈ 100 s + startup ≈ 120 s instead of 193 s; 16 cores further. | Medium: more load exposes the load-sensitive tests (AGENTS.md lists two browser ones). Fix them first. | Trivial (config) + fixes. |
| 6 | **Fix load-sensitive tests** (fixed timeouts, wall-clock assertions, shared ports). | Yes: AGENTS.md lists 1 dotnet, 2 browser, several npm; je12's 13-min run at load 48 failed on more. | Indirect but large: it is what allows #2, #5 and several gates at once. | Must not loosen assertions: replace waits on time with waits on the event, or make the budget relative to measured speed only where the assertion is about ordering, not time. | Medium, per test. |
| 7 | **Content-addressed result caching** (t3code `test:cached`, Bazel): skip a suite/file whose inputs are unchanged. | Partly. Node files: inputs are hard to enumerate statically (they read `js/**`, fixtures, `client/src` through esbuild); file-access tracing (t3code's `auto`) is the sound way. The typecheck is the clean case: its inputs are exactly `client/**`, the tsconfig and the TypeScript version. | Typecheck cache: ~3.7 s × 4–6 hits per gate (several on the critical path). Node-file caching: large in the inner loop, near zero in a merge gate (a merge changes many inputs). | Real: a key that misses an input gives a false pass. Mitigate as t3code does: key on traced reads, plus `--verify-hits` auditing; never in the merge gates without an audit. | Medium–large. |
| 8 | **Affected-tests selection** from the dependency graph (TS imports, feature map, C# references), fail-open like `ci-changes.cjs`. | Yes, as a separate inner-loop mode (the `quick` mode on `skill/je12-support` already selects by feature map, without import tracing). | Inner loop: seconds instead of minutes. Merge gates unchanged. | Misses are the risk; measured over history (RESULTS.md). | Medium. |
| 9 | **Faster type checker in the inner loop** (`tsgo`/TypeScript 7, ts-rust), `tsc` 6 stays the authority in the gates; a gate step runs both and fails on disagreement. | Yes for checking (esbuild does emit). The in-process TS 6 API in `client-build.mjs` stays (source policy and `parseJsonText` need it). | Measured (RESULTS.md §7): one full check of `client/` is 4.0–4.1 s with `tsc` 6, 0.51–0.54 s with TypeScript 7.0.2, 0.25–0.29 s with tsc-rs 0.8.0. In a gate that is ~4 s per check on whichever lane runs it; in the inner loop it is most of `quick`'s type-check step. | Accepting code `tsc` rejects; measured with a seeded-error set (121 mutations). | Small. |
| 10 | **Node test isolation off / Bun / Vitest swap.** | Not now: the jsdom suites rely on fresh globals per file (they patch `window`, prototypes, timers); a framework swap is churn without a measured need. | Unknown; would cut per-file import cost (~0.2–0.5 s jsdom import × 181 files ≈ 40–90 CPU-s). | High (shared state between files). | Large. |
